# 疑难问题与修复记录

> 返回 [主 README](../README.md)｜机型：HP 15s-dy0xxx / i7-8565U / UHD 620 / macOS Tahoe 26.7.2

本文汇总本机在黑苹果调试中遇到的、最容易误判或反复踩坑的问题。每条都按「现象 → 根因 → 处置 → 验证」记录，并尽量给出可复现的判断依据。部分根因来自对 WhateverGreen / AppleIntelFramebuffer / WebKit 的逆向与源码比对，文中会给出对应链接。

## 问题速查

| # | 问题 | 一句话结论 |
|:---:|:---|:---|
| 1 | `disable-agdc=1` 导致开机 20 分钟 | WEG 的 AGDC disabler 改变 `IOFBProbeOptions`（1 → 1025），不要使用 |
| 2 | `CNConnectorAlwaysConnected`（flags `0x0008`）导致黑屏 | 强制 `port-number=0` 与内屏 LVDS 的 port 0 冲突，外接 connector 绝不加 |
| 3 | connector 表字节写错导致卡启动 / 黑屏 | `plutil -data` 命令行会字节错位；用 `plistlib` 或 `-xml` 写入，并逐字段核对 |
| 4 | `framebuffer-patch-enable` 关掉 WEG 自动 DP→HDMI 补丁 | `hdmiAutopatch = !applyFramebufferPatch && ...`；要么全自动，要么全手写 |
| 5 | 诊断方法 | 必须 `-v`；macOS 26 上用 IORegistry 属性，不依赖 `IOLog` / `SYSLOG` |
| 6 | 其它已排除的坑 | `igfxonln` 不改 EDID、`-igfxmpc=600` 不解析、override EDID 只支持 128B 等 |
| 7 | Safari 外接 120Hz 仍 60fps | WebKit 偏好 `PreferPageRenderingUpdatesNear60FPSEnabled` 默认 true |

## 1. `disable-agdc=1` 导致开机 20 分钟

### 现象

- 开机进度条极慢，通常要走 **约 20 分钟** 才能进入桌面；
- 系统本身没有 panic，日志也没有明显报错；
- 移除该配置后，同一 EFI 开机恢复正常（几十秒级）。

### 根因

`disable-agdc` 是 WhateverGreen 提供的 AGDC（Apple Graphics Device Control）禁用开关。它会改变 AppleIntelFramebuffer 的 `IOFBProbeOptions`：正常情况下该值为 `1`，启用 AGDC disabler 后变为 **`1025`（`0x401`）**。这个额外的 bit 会让 framebuffer probe 进入一条异常的回退 / 等待路径，在本机上表现为长时间卡在启动阶段。

`IOFBProbeOptions` 是判断该问题的直接证据：

```bash
# 正常应接近 1；若看到 1025 / 0x401，检查是否启用了 disable-agdc
ioreg -lw0 | grep -i IOFBProbeOptions
```

### 处置

- **不要使用 `disable-agdc`**：从 `DeviceProperties` 中删除该键；若 boot-args 中有等价的 AGDC 关闭参数，也一并删除。
- 不要为了“让 AGDC 不工作”去叠加其他 framebuffer 属性；HDMI 修复与 AGDC 无关。
- 若已经写入且忘了备份，按第 5 节的单用户模式流程恢复 `config.plist.bak-*`。

### 验证

- 重启计时：正常应在数十秒内进入桌面；
- `ioreg` 中 `IOFBProbeOptions` 回到 `1`；
- 若仍慢，检查是否还有 `-igfxagdc` 类参数或其它 framebuffer 属性残留。

## 2. `CNConnectorAlwaysConnected`（connector flags bit `0x0008`）导致黑屏

### 现象

- 内屏或外接屏黑屏；
- `IODisplayConnect=0`，系统报告中显示器数量为 0；
- 但 `Display status=1`，看起来“显示器在线”，实际没有任何输出；
- 严重时内屏也被顶掉。

### 根因

`CNConnectorAlwaysConnected` 是 connector flags 的 bit `0x0008`，语义是“该连接器始终视为已连接”，通常用于 **内屏 / LVDS**。把它加到外接 HDMI connector（本机 `con1`）上时，系统会强制把该 connector 的 `port-number` 设为 `0`；而内屏 LVDS/eDP 本身占用 port 0，两者发生冲突，显示状态机进入“在线但无输出”的黑屏状态。

本机 `con0`（内屏）的 `flags=0x0098` 本身就包含 `0x0008`，这是内屏专用配置；**不能把这个值复制到 `con1`**。`con1` 应保持原生 `0x01C7`。

### 处置

- 外接 HDMI connector **绝不设置 `flags 0x0008`**；
- `con1` 保持 `flags=0x01C7`，`con2` 保持 `0x01C7`；
- 若需要“强制在线”，使用 boot-args 的 `igfxonln=1` / `igfxfcms=1`，不要改 connector flags；
- 修改后务必解码打印 `idx/bus/pipe/type/flags`，确认没有把 `0x01C7` 写成 `0x01CF` 或其它值。

### 验证

- `system_profiler SPDisplaysDataType` 能看到内屏与外接屏；
- `IODisplayConnect` 非 0；
- 若系统报告 0 显示器但 `Display status=1`，优先怀疑 flags 被改错。

## 3. connector 表字节写错导致卡启动 / 黑屏

### 现象

- 修改 `framebuffer-con0-alldata` 后开机卡住、黑屏，或内屏正常但 HDMI 消失；
- 解码后发现字段与预期不一致，例如本想写 `00000800 / 01C7`，实际变成 `03000800 / 0107`；
- 用 `plutil -data` 从命令行传 base64 时最容易出现。

### 根因

`plutil -data` 的命令行参数处理会把 base64 字符串按 shell / plutil 的规则重新解释，导致字节错位或截断；connector 记录是 12 字节定长结构，任何 1 字节偏移都会让 `type` / `flags` 整体错位。OpenCore 不会校验这些字段的语义，错误值会直接被 WhateverGreen / AppleIntelFramebuffer 使用，表现为卡启动或黑屏。

### 处置

**优先使用 Python `plistlib` 直接读写**（不经过 shell 的 base64 转换）：

```python
import plistlib
from pathlib import Path

path = Path("config.plist")
with path.open("rb") as f:
    cfg = plistlib.load(f)

dev = cfg["DeviceProperties"]["Add"]["PciRoot(0x0)/Pci(0x2,0x0)"]
data = dev["framebuffer-con0-alldata"]
assert len(data) == 36, f"expect 36 bytes, got {len(data)}"

for i in range(3):
    rec = data[i * 12:(i + 1) * 12]
    idx = rec[0]
    bus = rec[1]
    pipe = rec[2]
    typ = int.from_bytes(rec[3:7], "little")
    flags = int.from_bytes(rec[7:11], "little")
    print(f"con{i}: idx={idx} bus=0x{bus:02X} pipe=0x{pipe:02X} "
          f"type=0x{typ:04X} flags=0x{flags:04X}")

# 确认无误后再写回；写回前先备份
with path.open("wb") as f:
    plistlib.dump(cfg, f, fmt=plistlib.FMT_XML, sort_keys=False)
```

也可以使用 `plutil` 的 XML 值形式，避免命令行 base64 解析：

```bash
plutil -replace 'DeviceProperties.Add.PciRoot(0x0)/Pci(0x2,0x0).framebuffer-con0-alldata' \
  -xml '<data>AAAIAAIAAACYAAAAAQEJAAAIAADHAQAAAgQKAAAEAADHAQAA</data>' config.plist
```

**每次改完必须解码打印 `idx / bus / pipe / type / flags` 逐字段核对**，并与下表比对：

| Connector | idx | busId | pipe | type | flags |
|:---|:---:|:---:|:---:|:---:|:---:|
| con0 | 0 | `0x00` | `0x08` | `0x0002` | `0x0098` |
| con1 | 1 | **`0x01`** | `0x09` | `0x0800` | `0x01C7` |
| con2 | 2 | `0x04` | `0x0A` | `0x0400` | `0x01C7` |

### 备份与恢复

- 修改前：`cp config.plist config.plist.bak-$(date +%Y%m%d-%H%M%S)`；
- 修改后：至少保留一份能启动的备用 EFI；
- 若已无法启动：按第 5 节的 `Cmd+S` 单用户流程恢复备份。

## 4. `framebuffer-patch-enable` 会关掉 WEG 自动 DP→HDMI 补丁

### 现象

- 原本 HDMI 可以用，加入 `framebuffer-patch-enable=1` 或某些手写 connector 属性后 HDMI 反而黑屏；
- 或只改了 `con1` 的一部分字段，HDMI 就失效。

### 根因

WhateverGreen 的 HDMI 自动补丁逻辑是：

```cpp
bool hdmiAutopatch = !applyFramebufferPatch && ...;
```

`framebuffer-patch-enable` 一旦为真，`applyFramebufferPatch` 即为真，**WEG 的自动 DP→HDMI 补丁被整体关闭**。此时系统完全依赖你手写的 connector 表；如果只写了半套（例如只改 `con1-type`，没写 `con1-busId` / `pipe` / `flags`），就会得到不完整甚至互相矛盾的 connector 配置。

### 处置

二选一，不要半套：

1. **全自动**：删除 `framebuffer-patch-enable` 与所有 `framebuffer-conX-*` 手写属性，让 WEG 自动识别并打补丁；
2. **全手写**：保留 `framebuffer-patch-enable=1`，并一次性写完整的 36 字节 `framebuffer-con0-alldata`（con0 / con1 / con2 三段齐全），不要只写 `con1` 的半套字段。

本机最终采用第 2 种：完整的 36 字节表 + `framebuffer-patch-enable=1`。如果只想做最小化 patch，则改用 `framebuffer-con1-enable` + `framebuffer-con1-busid` + `framebuffer-con1-type` + `framebuffer-con1-flags` 的完整组合，不要与 `con0-alldata` 混用。

### 验证

- 解码并核对三个 connector 的所有字段；
- 若不亮，临时删除 `framebuffer-patch-enable` 与手写表，确认 WEG 自动路径是否能点亮，以判断问题是否出在手写表。

## 5. 诊断方法论

### 5.1 启动问题必须加 `-v`

任何“卡启动 / 黑屏 / 花屏”问题，第一步都是加 `-v debug=0x100 keepsyms=1`，保留完整启动日志。没有 `-v` 时，OpenCore 只会显示苹果 logo，无法判断卡在哪个 kext / 哪个阶段。

### 5.2 macOS 26 上不要依赖 Lilu 插件的 `IOLog` / `SYSLOG`

macOS 26（Tahoe）对第三方 kext 的日志输出限制更严，Lilu 插件的 `IOLog` / `SYSLOG` 经常无法进入 `log show`。优先使用 **IORegistry 属性** 作为观测面：

```bash
# 例：RealtekBTPatcher 的注入计数
ioreg -lw0 | grep -oE '"IBTP[A-Za-z]+" = <[^>]*>'

# 例：framebuffer 探针选项
ioreg -lw0 | grep -i IOFBProbeOptions
```

如果必须看 WEG 的 framebuffer 调试日志，使用 DEBUG 版 WhateverGreen 并加 `-igfxfbdbg`；但要注意 **不要与 `disable-agdc` 同时使用**，两者组合会 PANIC（见 5.3）。

### 5.3 WEG DEBUG 与 `disable-agdc` 不可同用

- `-igfxi2cdbg` 可以打开 WEG 的 I2C / framebuffer 调试输出；
- 但它与 `disable-agdc` 同时存在时，本机实测会触发 **kernel panic**；
- 排查顺序：先移除 `disable-agdc`，再加 `-igfxi2cdbg`；不要反过来。

### 5.4 恢复流程：`Cmd+S` 单用户 → 挂载 ESP → 恢复备份

当 `config.plist` 改错导致无法进入系统时：

1. 开机按住 **`Cmd+S`** 进入单用户模式（FileVault 开启时可能需要先解锁）；
2. 挂载 ESP：

   ```bash
   diskutil list
   diskutil mount disk0s1        # 以实际 ESP 的 diskXsY 为准
   ```

3. 进入 OpenCore 目录并恢复备份：

   ```bash
   cd /Volumes/EFI/EFI/OC
   ls -l config.plist.bak-*
   cp config.plist.bak-20260101-120000 config.plist   # 换成你的备份文件名
   ```

4. 确认文件大小 / 校验和正确后 `reboot`；
5. 若单用户模式也无法进入，用另一块 EFI 或 Windows / Linux 启动盘挂载 ESP 替换。

> 每次修改 `config.plist` 前都先生成带时间戳的备份；不要只留一份“最终版”。

## 6. 其它已排除的坑

| 坑 | 实际情况 | 正确做法 |
|:---|:---|:---|
| `igfxonln` / `force-online` 能修 EDID | 只改 `getDisplayStatus` 的在线状态，不改变 EDID 内容 | EDID 问题用 `AAPL01,override-no-connect`（128 字节） |
| `-igfxmpc=600` 能提高像素时钟 | WEG 只识别裸标志 `-igfxmpc`，不解析 `=600`；内部固定 675MHz | 写成 `-igfxmpc`，不要带数值 |
| `AAPL0X,override-no-connect` 可写 256 字节 | 只支持 **128 字节**；256 字节 / DisplayID 扩展不会被读取 | 只注入前 128 字节，必要时裁剪扩展块 |
| `enable-hdmi20` / `-cdfon` 能在新系统启用 HDMI 2.0 | macOS 11+ 已不再实现该路径 | 不要把 4K60 希望寄托在该参数上；本机无 LSPCON，4K60 不可行 |
| `STATUS 4803` 一定是蓝牙故障 | 成功配对日志中同样会出现 `STATUS 4803` / `isPairing=0` | 以 `ready-state`、`smpPairingCompleted status` 为准 |
| `rtl8821c_config.bin` 是 LE 特性开关 | 它是 Realtek 固件配置 / RF 参数文件，不是 HCI feature bitmap | 不要通过替换该文件来“开启 LE” |
| `disable-agdc` 能解决显示问题 | 会把 `IOFBProbeOptions` 从 1 改成 1025，导致 20 分钟开机 | 不要使用；HDMI 用 connector + `igfxonln` / `igfxfcms` 解决 |

## 7. Safari 外接 120Hz 仍 60fps

### 现象

- 外接显示器在系统信息 / 显示器设置中已确认 **120Hz**；
- 桌面、Chrome、Firefox 可能正常，但 **Safari 页面动画、滚动、testufo 仍显示 60fps**；
- 换 120Hz 显示器、换线、改分辨率都无效。

### 根因

WebKit 有一个隐藏偏好 **`PreferPageRenderingUpdatesNear60FPSEnabled`**，默认值为 `true`。它会把页面渲染更新频率压到接近 60fps，即使 `DisplayLinkMac` 已经从显示器拿到 120Hz 的刷新率。相关实现位于：

- [`DisplayLinkMac.cpp`](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/mac/DisplayLinkMac.cpp)：显示链接与刷新率同步；
- [`Page.cpp`](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/page/Page.cpp)：页面渲染更新调度；
- [`AnimationFrameRate.cpp`](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/graphics/AnimationFrameRate.cpp)：动画帧率与 60fps 偏好；
- [`UnifiedWebPreferences.yaml`](https://github.com/WebKit/WebKit/blob/main/Source/WTF/Scripts/Preferences/UnifiedWebPreferences.yaml)：`PreferPageRenderingUpdatesNear60FPSEnabled` 的定义。

### 修复（GUI）

1. 打开 **Safari → 设置 → 高级**；
2. 勾选 **「显示网页开发者功能」**（Show features for web developers）；
3. 菜单栏出现 **「开发」** 菜单，进入 **开发 → 功能标志**（Feature Flags）；
4. 搜索 **“Prefer Page Rendering Updates near 60fps”**；
5. **取消勾选**；
6. **`Cmd+Q` 完全退出 Safari**，再重新打开（只关窗口不够）。

### 修复（命令行，备用）

先完全退出 Safari，再执行：

```bash
defaults write com.apple.Safari WebKitPreferPageRenderingUpdatesNear60FPSEnabled -bool false
```

然后重新打开 Safari。若系统设置有“还原 / 同步”，确认该偏好没有被 iCloud 或配置描述文件覆盖。

### 验证

- 打开 <https://www.testufo.com/refreshrate>，确认显示 120fps（或接近显示器刷新率）；
- 用 Safari 打开一个高帧率动画页面，与 Chrome / Firefox 对比；
- 若 **Chrome / Firefox 也只有 60fps**，说明限制在系统层（显示器链路、WindowServer 合成或线材 / 接口带宽），不是 WebKit 偏好；此时应回到显示器设置与 HDMI 链路排查；
- 若只有 Safari 是 60fps，按上述偏好修改即可。

## 8. 修改前的检查清单

- [ ] 已备份 `config.plist` 与整个 `EFI` 文件夹；
- [ ] 已确认当前 `config.plist` 能被 `ocvalidate` 通过；
- [ ] 一次只改一个变量（connector、boot-arg、kext 之一）；
- [ ] 修改 connector 后已用 `plistlib` / `plutil` 解码并逐字段核对；
- [ ] 已保留可启动的备用 EFI（U 盘或另一分区）；
- [ ] 出现黑屏 / 卡启动时，先加 `-v` 并记录最后一行日志，再按第 5 节恢复。
